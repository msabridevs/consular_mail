# دليل الاستخدام والتشغيل

## سير الظرف

1. **بانتظار استلام القسم:** موظف الوارد يسجل رقم الإرسال واسم المرسل والقسم والمبلغ الفعلي داخل الظرف. التاريخ والوقت يصدران من قاعدة البيانات.
2. **قيد العمل:** مسؤول القسم يطابق الأظرف الفعلية، يحدد المستلمة، ويضغط تأكيد الاستلام مرة واحدة. لا يلزم فتح كل ظرف إلكترونيًا.
3. **بانتظار استكمال:** يكتب المسؤول ملاحظة عامة واضحة، يحفظها، ثم يحدد الظرف ويضغط طلب استكمال. عند وصول الاستكمال يضغط استئناف العمل.
4. **أُعيد بالبريد:** بعد التسليم الفعلي للإرسال، يحدد المسؤول الأظرف المنجزة ويضغط تأكيد الإعادة؛ تظهر رسالة تأكيد قبل إعلانها للجمهور. الاستلام والإعادة يسجلان هوية المنفذ والوقت.

يمكن تحديد كل الصفحة (50 ظرفًا) وتنفيذ إجراء جماعي. الأزرار تعمل فقط إذا كانت جميع الأظرف المحددة في الحالة المناسبة. تحديث الصفحة يمسح التحديد؛ العملية تحفظ كل الصفوف معًا أو تتراجع كلها إذا تغيّر أحدها. ترتيب القفل ثابت لتقليل تعارض العمليات المتزامنة.

الإعادة متاحة من قيد العمل فقط. من حالة انتظار الاستكمال يجب أولًا استئناف العمل. لا يمكن إعادة الاستلام أو الإعادة مرتين. لا يوجد حذف من الواجهة، ولا عكس لحالة الإعادة من حساب موظف.

## قواعد البيانات اليومية

- المقصود بالمبلغ: المبلغ النقدي المسجل داخل المظروف باليورو، وليس دفتر حسابات أو إيصالًا رسميًا أو احتسابًا آليًا لرسوم الخدمة.
- لا تُدخل صور جوازات أو أرقام هوية أو ملفات؛ النسخة مصممة لتتبع البريد فقط.
- رقم الإرسال الوارد فريد في هذه النسخة. تُزال المسافات وتُحوّل الحروف إلى الكبيرة. تدعم الواجهة تحويل الأرقام العربية إلى أرقام لاتينية. الحد 6–50 رمزًا من الحروف اللاتينية والأرقام والشرطة. إذا كانت شركة البريد تستخدم تنسيقًا مختلفًا، عدّل تحقق العميل وقيد SQL معًا بعد الاختبار.
- لا تضف بادئة سرية إلى رقم الإرسال لحل تكراره؛ المواطن يستخدم الرقم الأصلي. إذا أُعيد استعمال رقم من شركة البريد بعد سنوات، يجب حسم أرشفة السجل وسياسة البحث قبل إدخال نفس الرقم؛ النسخة الحالية تمنع التكرار بدل عرض طلب ملتبس.
- الأوقات تُخزن timestamptz وتُعرض بتوقيت Europe/Berlin، بما فيه التحول الصيفي. لا يعتمد وقت التسجيل على ساعة الموظف.
- «متجاوز 7 أيام» يعني أكثر من 168 ساعة منذ التسجيل ولم يُعد؛ يشمل انتظار الاستكمال. ليس مهلة قانونية ولا تقييمًا تلقائيًا للموظف.
- متوسط الإنجاز يحسب من التسجيل إلى الإعادة لكل المعاد في القسم، بالأيام التقويمية. العدادات عامة لكل الأقسام المصرح بها ولا تتغير بفلاتر جدول البريد.
- المعاد اليوم محسوب حسب تاريخ ألمانيا. القوائم تحدث كل 30 ثانية عندما تكون الصفحة نشطة وليست نافذة التفاصيل مفتوحة. زر تحديث متاح فورًا.

## الملاحظات الثنائية اللغة

النصوص الثابتة مترجمة. الملاحظات التي يكتبها الموظف لها خانتان مستقلتان: عربية وألمانية. لا توجد ترجمة آلية ولا إرسال للنص إلى خدمة ذكاء اصطناعي. إذا كانت لغة واحدة متاحة، تُعرض للمواطن مع بيان عدم توفر النسخة المختارة.

اكتب مثلًا: «يرجى التواصل مع القسم لاستكمال المستندات المطلوبة.» / «Bitte wenden Sie sich an die zuständige Abteilung, um die erforderlichen Unterlagen zu ergänzen.»

رقم الإرسال ليس إثبات هوية. يستطيع من يعرفه رؤية الحالة والملاحظات العامة؛ لذلك لا تضع في الملاحظة العامة معلومات شخصية أو أسبابًا حساسة. Turnstile والحد من المحاولات يحدان من البحث الآلي، ولا يضمنان سرية الرقم. إذا احتاج العمل عرض معلومات شخصية مستقبلًا، أضف رمز تحقق منفصلًا أو دخولًا موثقًا بدل توسيع الاستعلام الحالي.

## الصلاحيات

| الدور | ما يراه | ما يعدله |
|---|---|---|
| intake | بريد جميع الأقسام وسجل الحركة | تسجيل جديد فقط |
| officer | الأقسام المسندة فقط | الاستلام، الاستكمال، الإعادة، الملاحظات ورقم الإعادة |
| consul | الأقسام المسندة فقط ومؤشراتها | قراءة فقط |
| admin | جميع الأقسام | التسجيل والحركة والملاحظات وتصحيح بيانات التسجيل |

التصحيح الإداري متاح من التفاصيل. يمكن تغيير القسم قبل استلامه فقط؛ التصحيح بعد الاستلام لا يسمح بنقل الملف لقسم آخر. سجل الحركة يحتفظ بالقيم السابقة واللاحقة. مدير النظام داخل التطبيق لا يستطيع تعيين أدوار بنفسه؛ التعيين يحتاج إدارة Supabase الموثوقة.

الجداول الخاصة غير مكشوفة عبر API ولا تمنح مستخدمي التطبيق أي وصول مباشر. تفعيل RLS بلا سياسات يمنع وصول الأدوار العادية، وتعمل وظائف security definer المحددة بفحص الهوية والعامل الثاني والدور والقسم. لا تُغيّر منح EXECUTE أو expose مخطط private دون مراجعة.

## تعطيل موظف أو نقل اختصاصه

نفّذ من SQL Editor بحساب إدارة قاعدة البيانات، بعد استبدال البريد:

```sql
update private.staff set active=false
where user_id=(select id from auth.users where lower(email)=lower('EMPLOYEE_EMAIL'));
```

هذا يمنع عمليات البيانات التالية حتى لو بقيت جلسة Auth مفتوحة؛ البيانات التي سبق تحميلها على جهازه لا يمكن سحبها بأثر رجعي. أنهِ جلساته وراجع جهاز العمل حسب إجراءات الجهة. لإعادة التفعيل أو تغيير الدور والأقسام استخدم قالب `002_staff-template.sql` بالقيم الجديدة؛ القالب يعيد active=true عمدًا.

لفقدان كلمة المرور: مسؤول Auth يضبط كلمة مرور مؤقتة من بيئة موثوقة باستخدام إدارة Supabase. لفقدان TOTP: تحقق من هوية الموظف خارج النظام ثم أزل العامل المفقود عبر Auth Admin المعتمد؛ عند دخوله يطلب التطبيق إعداد عامل جديد. لا تلغِ شرط aal2 لحل المشكلة. هذه النسخة لا تطبق استعادة عامة بالبريد ولا رموز استرداد ذاتية.

## النسخ الاحتياطي والاحتفاظ

اعتمد جدول نسخ احتياطي في Supabase حسب الخطة واختبر الاستعادة دوريًا على مشروع منفصل. احتفظ بنسخة الكود في GitHub؛ GitHub ليس نسخة لبيانات Supabase. يتضمن سجل الأحداث نسخًا من الاسم والرسوم والملاحظات السابقة، لذلك لا يكفي مسح الحقول الحالية وحدها لتنفيذ سياسة إزالة البيانات. لا توجد عملية حذف تلقائي في هذا المشروع كي لا تحذف سجلات قبل اعتماد مدة الاحتفاظ رسميًا. يجب أن تشمل سياسة الاحتفاظ السجلات والأحداث والنسخ الاحتياطية.

الاستعادة تعيد حالة زمنية وقد تفقد الحركات اللاحقة؛ قارنها بدفتر استلام البريد قبل العودة للعمل. صلاحيات مالك قاعدة البيانات ومفتاح الخدمة يمكنهما تجاوز قيود التطبيق، والسجل ليس دفترًا غير قابل للتغيير أمام مالك قاعدة البيانات. قلل وصول الإدارة وأمّن حسابات المنصات بعامل ثانٍ.

## حدود هذه النسخة

- الإغلاق هنا إغلاق حسابات وصلاحيات، لا عزل شبكي. حصر الاستخدام داخل مقر البعثة يحتاج بوابة وصول إضافية تغطي البيانات كذلك؛ إخفاء `/staff` أو وضع قائمة IP عليه وحده لا يمنع استدعاء Supabase خارج الشبكة باستخدام بيانات دخول صحيحة.
- لا إرسال SMS أو بريد إلكتروني للمواطن، ولا ربط مباشر مع DHL/Deutsche Post، ولا استخراج رقم الإرسال من صورة.
- الطباعة للعرض الحالي، أي الصفحة الحالية فقط؛ ليست تصدير قاعدة كاملة.
- لا يوجد تطبيق لإدارة الحسابات من داخل النظام؛ الإدارة تتم عبر Supabase والقالب والسكربت.
- لا تحصيل إلكتروني، ولا تسوية خزينة، ولا تعدد عملات.
- الغرض تتبع الأظرف؛ ليس نظام توثيق معاملات قنصلية شاملًا أو نظام مراسلات دبلوماسية سرية.
