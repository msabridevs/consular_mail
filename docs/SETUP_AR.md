# دليل التنفيذ الكامل — من الملفات إلى التشغيل

## 1. النتيجة التي ستحصل عليها

رابط عام مثل `https://mail.example.org` للاستعلام، ورابط `https://mail.example.org/staff` للموظفين. بعد الدخول تظهر الأدوات بحسب الحساب، فلا تحتاج أربعة تطبيقات منفصلة. القنصل يرى قسمًا واحدًا أو عدة أقسام حسب ما تسنده إليه.

الخدمات المطلوبة: Supabase، GitHub، Vercel، وCloudflare Turnstile للتحقق من الاستعلام العام. Turnstile طبقة إضافية للحماية، وليس قاعدة بيانات إضافية. يمكنك استخدامه دون نقل استضافة الموقع أو أسماء النطاقات إلى Cloudflare.

استخدم حسابات مؤسسية يملكها العمل. ابدأ بمشروع تجريبي خالٍ من بيانات المواطنين. لا يثبت هذا الدليل أن أي خطة استضافة بعينها معتمدة لدى الوزارة.

## 2. إنشاء Supabase

1. افتح https://supabase.com/dashboard وأنشئ مشروعًا جديدًا.
2. اختر منطقة أوروبية مناسبة لسياسة الجهة؛ Frankfurt إذا كانت متاحة ضمن خياراتك. اختيار منطقة واحدة لا يعني أن جميع الخدمات المتصلة لا تعالج بيانات خارجها.
3. احتفظ بكلمة مرور قاعدة البيانات في مدير كلمات مرور.
4. افتح **SQL Editor**، وانسخ ملف `supabase/001_schema.sql` كاملًا وشغله **مرة واحدة على المشروع الجديد**. الملف معاملة واحدة؛ إذا فشل لا تكمل قبل إصلاح الخطأ. لا تعاود تشغيله على قاعدة مثبتة.
5. من إعدادات API انسخ Project URL والمفتاح العام publishable أو anon. انسخ أيضًا مفتاح `service_role` للخادم فقط.
6. لا تضف مخطط `private` إلى Exposed schemas. اترك `public` مكشوفًا لوظائف RPC المحددة. لا تنشئ سياسات قراءة عامة على الجداول.
7. في Authentication، أبق الدخول بالبريد وكلمة المرور مفعّلًا، وأغلق إنشاء الحسابات الجديدة للجمهور، وأغلق anonymous sign-ins. لا يوجد تسجيل ذاتي في التطبيق أصلًا، لكن تعطيله في Supabase ضروري أيضًا.
8. فعّل TOTP MFA enrollment وverification. التطبيق يفرض مستوى `aal2` داخل قاعدة البيانات، وليس في الشاشة فقط.
9. اضبط الحد الأدنى لكلمة المرور على 12 حرفًا، وفعّل وسائل حماية كلمات المرور المتاحة لخطة الجهة.
10. ضع Site URL على رابط التطبيق. لا تحتاج روابط تسجيل أو OAuth في هذه النسخة: الحسابات تُنشأ إداريًا، وكلمات المرور تُغير من مساحة الموظف.

## 3. إنشاء حسابات الموظفين وإسناد الأقسام

### الطريقة الأسهل من لوحة Supabase

من Authentication → Users → Add user / Create user أنشئ حسابًا بالبريد الوظيفي وكلمة مرور قوية، مع تأكيد البريد إداريًا إذا ظهر هذا الخيار. لا ترسل دعوة بريدية لأن مسار الدعوات غير مطبق هنا.

ثم افتح `supabase/002_staff-template.sql`، وضع البريد والاسم والدور والقسم الصحيح، وشغل الملف من SQL Editor. عند عدم وجود مستخدم بالبريد المحدد يتوقف الملف برسالة واضحة.

| الحساب | staff_role | staff_departments |
|---|---|---|
| مدير النظام | `admin` | `array[]::private.department[]` |
| موظف الوارد | `intake` | `array[]::private.department[]` |
| مسؤول التصديقات | `officer` | `array['legalization']::private.department[]` |
| مسؤول التأشيرات | `officer` | `array['visas']::private.department[]` |
| مسؤول الجوازات | `officer` | `array['passports']::private.department[]` |
| مسؤول الأحوال المدنية | `officer` | `array['civil']::private.department[]` |
| قنصل الجوازات والأحوال المدنية | `consul` | `array['passports','civil']::private.department[]` |
| قنصل يتابع كل الأقسام | `consul` | `array['legalization','visas','passports','civil']::private.department[]` |

يمكن تعدد الموظفين في نفس القسم. يمكن للموظف أو القنصل أن يُسند إلى أكثر من قسم. الحساب غير المسجل في جدول staff لا يستطيع الوصول إلى بيانات العمل حتى لو كان دخوله في Auth صحيحًا.

### بديل عند عدم توفر إنشاء المستخدم بكلمة مرور في اللوحة

على جهاز مسؤول موثوق، بعد تثبيت Node.js 22 أو أحدث:

```bash
npm ci
cp .env.example .env
# املأ SUPABASE_URL وSUPABASE_SERVICE_ROLE_KEY داخل .env محليًا
node --env-file=.env scripts/manage-staff.mjs
```

يسأل السكربت عن البريد فقط، وينشئ كلمة مرور مؤقتة قوية، ويعرضها مرة واحدة في الطرفية. نفذه في جلسة خاصة غير مسجلة، وسلم الكلمة للموظف عبر وسيلة معتمدة، ثم احذفها من سجل الطرفية. السكربت لا يمنح صلاحيات التطبيق؛ أكمل قالب SQL. لا تشغله في GitHub Actions أو Vercel logs.

### أول دخول

الموظف يدخل من `/staff` بالبريد وكلمة المرور، ثم يضغط إعداد تطبيق المصادقة ويمسح QR في تطبيق معتمد مثل تطبيق TOTP الموجود لدى الجهة. يدخل الرمز لتفعيل العامل الثاني. بعدها تظهر مساحة العمل. يغيّر كلمة المرور من زر تغيير كلمة المرور. عند كل جلسة جديدة يحتاج كلمة المرور ورمز التطبيق. لا تُشارك الحسابات بين الموظفين.

## 4. رفع المشروع إلى GitHub

فك الضغط. المجلد الذي يحتوي `package.json` هو جذر المشروع. أنشئ مستودعًا **خاصًا** باسم مثل `consular-mail-frankfurt`.

بالطرفية من داخل هذا المجلد:

```bash
git init
git add .
git commit -m "Initial consular mail application"
git branch -M main
git remote add origin https://github.com/YOUR_ORG/consular-mail-frankfurt.git
git push -u origin main
```

استبدل YOUR_ORG. استخدم وسيلة مصادقة GitHub المعتادة دون وضع token في عنوان المستودع. `.gitignore` يمنع رفع `.env` و`node_modules`. راجع الملفات المرحلية قبل أول commit؛ لا ترفع أسرارًا أو نسخ قواعد البيانات. يوجد workflow لتشغيل الاختبارات والبناء مع كل push وpull request.

## 5. إعداد Turnstile

1. افتح لوحة Cloudflare → Turnstile وأنشئ widget للمشروع.
2. اختر Managed، وأضف اسم النطاق المستقر الذي سيستخدمه الجمهور، مثل `mail.example.org` أو اسم مشروع Vercel المستقر `YOUR_PROJECT.vercel.app`.
3. انسخ Site key العام وSecret key السري.
4. لا تستخدم مفاتيح الاختبار في الإنتاج. لا تضف جميع أسماء النطاقات عشوائيًا.

إذا لم تعرف رابط Vercel بعد، أنشئ مشروع Vercel أولًا، انسخ اسمه المستقر، ثم أكمل إعداد Turnstile ومتغيرات البيئة وأعد النشر. النشر دون متغيرات يعرض أن الإعداد غير مكتمل ولا يفتح البيانات.

## 6. النشر على Vercel

1. افتح https://vercel.com/new واربط مستودع GitHub الخاص.
2. اختر Framework: **Vite**. الجذر هو المجلد الذي يحتوي `package.json`، وليس `src` أو `dist`.
3. Build command: `npm run build`؛ Output directory: `dist`؛ Install command: `npm ci`. اختر Node.js 22 أو أحدث مدعومًا من Vercel.
4. أضف متغيرات البيئة التالية إلى بيئة **Production**. لا تُعد استخدام مفاتيح الإنتاج في فروع Preview العامة أو غير الموثوقة.

| المتغير | القيمة | هل يصل إلى المتصفح؟ |
|---|---|---|
| `VITE_SUPABASE_URL` | Project URL | نعم |
| `VITE_SUPABASE_ANON_KEY` | publishable / anon key | نعم، ومسموح تصميميًا |
| `VITE_TURNSTILE_SITE_KEY` | Turnstile Site key | نعم |
| `SUPABASE_URL` | نفس Project URL | لا |
| `SUPABASE_SERVICE_ROLE_KEY` | مفتاح service_role | لا، سر قوي جدًا |
| `TURNSTILE_SECRET_KEY` | Turnstile Secret key | لا |
| `TURNSTILE_HOSTNAME` | `YOUR_PROJECT.vercel.app` أو `mail.example.org` فقط، بلا https أو مسار | لا |
| `APP_ORIGIN` | `https://YOUR_PROJECT.vercel.app` أو `https://mail.example.org` بلا شرطة مائلة في النهاية | لا |
| `RATE_LIMIT_SECRET` | قيمة عشوائية قوية، 64 خانة hex مثلًا | لا |

لتوليد RATE_LIMIT_SECRET على جهازك:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

**لا تسمِّ أي مفتاح سري باسم يبدأ بـ`VITE_`.** كل متغير يبدأ بذلك قد يصبح جزءًا من ملفات المتصفح عند البناء. المفتاح العام ليس كلمة مرور الموظفين؛ صلاحيات قاعدة البيانات هي التي تحمي البيانات.

5. اضغط Deploy. دالة `/api/track` تُنشر تلقائيًا من مجلد `api`، وملف `vercel.json` يضبط `/staff` وترويسات الحماية.
6. افتح رابط Production المستقر. الرابط العشوائي الخاص بنسخة Preview ليس بديلًا عن APP_ORIGIN.
7. عند تعديل أي متغير VITE أعد البناء والنشر. أعد النشر أيضًا بعد تغيير مفاتيح الخادم لتطبيق إعدادات النسخة الجديدة.
8. عند إضافة نطاق مخصص، حدّث APP_ORIGIN وTURNSTILE_HOSTNAME والنطاق المسموح في Turnstile. يستخدم API نطاقًا واحدًا معتمدًا؛ استخدم تحويلًا إلى النطاق الأساسي لبقية الأسماء.
9. اجعل GitHub والمشروع ولوحة الإدارة متاحين لفريق الإدارة فقط. لا تضع حماية Vercel لكامل موقع الإنتاج إذا كان ذلك سيمنع الجمهور من الاستعلام.

## 7. الاختبار قبل البيانات الفعلية

أنشئ حسابات تجربة للأدوار المختلفة. أدخل أرقامًا وهمية فقط.

1. موظف الوارد يسجل `TEST000001` إلى التصديقات باسم وهمي ومبلغ 12.34.
2. تحقق أن التاريخ تلقائي، وأن تكرار الرقم يُرفض.
3. مسؤول التأشيرات لا يرى المظروف. مسؤول التصديقات يرى العدد والمظروف.
4. يحدد مسؤول التصديقات المظروف ويؤكد الاستلام؛ يجب أن تصبح الحالة قيد العمل.
5. يدخل ملاحظتين عامتين بالعربية والألمانية، وملاحظة داخلية مختلفة.
6. من نافذة خاصة، استعلم برقم الإرسال؛ لا يظهر الاسم أو الرسوم أو الملاحظة الداخلية.
7. اختبر طلب الاستكمال ثم استئناف العمل ثم تأكيد الإعادة.
8. افتح حساب القنصل؛ تحقق من العدادات وسجل الحركة وأنه لا يستطيع تعديل البيانات.
9. اختبر قسمين، وعملية جماعية، ومحاولتين لتعديل نفس السجل من جلستين. عند التعارض يجب تحديث القائمة؛ لا تتكرر الحركة.
10. جرّب اللغتين على الهاتف والحاسوب. اطبع العرض الحالي للتأكد من ملاءمته لعملك.

للاختبارات البرمجية:

```bash
npm ci
npm test
npm run build
```

## 8. التشغيل المحلي الكامل، إذا احتجته

الأبسط للاختبار التشغيلي هو نشر تجريبي منفصل على Vercel بقاعدة تجريبية. محليًا:

```bash
npm ci
cp .env.example .env
npx vercel dev --listen 3000
```

اضبط APP_ORIGIN على `http://localhost:3000` وTURNSTILE_HOSTNAME على hostname الفعلي الذي يرجعه Turnstile للتطوير؛ استخدم widget تطوير مخصصًا يدعم localhost. لا تنقل هذه القيم للإنتاج. وثائق Turnstile تشرح مفاتيح الاختبار؛ بعض مفاتيح الاختبار ترجع hostname تجريبيًا مختلفًا، فلا تُعطل فحص hostname/action لمجرد تمرير اختبار محلي. اختبارات API في المستودع تحاكي Turnstile ولا تحتاج اتصالًا خارجيًا.

## 9. الأخطاء الأكثر شيوعًا

| ما يظهر | ما تراجعه |
|---|---|
| يلزم ضبط الاتصال | متغيرا VITE_SUPABASE ووجود Redeploy بعد تعديلهما |
| الحساب غير مصرح | staff.active، الدور والأقسام، وإتمام TOTP؛ وجود حساب Auth وحده غير كاف |
| فشل التحقق الأمني | hostname، Site key/Secret key المتطابقان، action=track، والنطاق الفعلي |
| الخدمة غير متاحة | مفاتيح الخادم، تشغيل SQL migration، وبيئة Production الصحيحة |
| كثير من المحاولات | الحد 20 محاولة لكل عنوان IP خلال 10 دقائق؛ مكاتب مشتركة قد تتشارك العنوان |
| التعارض | مستخدم آخر عدّل السجل؛ أغلق التفاصيل وحدّث ثم افتحه مجددًا |
| /staff لا يفتح | وجود vercel.json في جذر المشروع وعدم استبدال rewrite |
| كلمة المرور لا تتغير | راجع سياسة Supabase؛ إذا تطلبت إعادة مصادقة فسجّل الخروج ثم ادخل من جديد وحاول |
| القاعدة موجودة لكن SQL يعطي already exists | ملف التأسيس نُفذ من قبل؛ لا تعاود تشغيله ولا تحذف القاعدة لحل الخطأ |

لا ترسل مفاتيح الخدمة أو كلمات المرور في رسائل الدعم أو لقطات الشاشة.
